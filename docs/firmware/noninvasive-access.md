# Non-invasive firmware access

## Verified observations

Three guided test arrangements and four successful Windows hub enumerations produced only the normal USB-MIDI identity. Normal-mode BLE discovery found Generic Access and BLE MIDI only. There is currently no verified firmware access or local factory backup. [Startup and GATT experiment](../experiments/2026-11-26-noninvasive-firmware-access.md)

## Documented reference paths

- **Dream SAM5000 DFU.** The reference implements a separate bootloader, generally in external flash, with board firmware deciding whether a startup input requests DFU or the application starts. Dream's descriptor tool allows custom runtime and boot identities. The 5704FX example uses `2485:4f2e` in DFU, and another reference package uses `2485:4f30`. The published 5704PIA startup keys refer to that piano development board. Their behavior has no established correspondence to the EWI. [Dream SAM5000 DFU guide](https://docs.dream.fr/progsam/Dream_DFU_Tools/SAM5000_DFU.pdf) · [5704PIA reference manual](https://docs.dream.fr/pdf/Serie5000/Firmwares/5704PiaRef%20UsersManual.pdf) · [Reference artifact comparison](../experiments/2026-11-26-dream-reference-files.md)
- **DreamDFU discovery.** Dream distributes a customizable GUI for known, driver-accessible DFU targets. Its guide describes scanning and device matching in the update workflow, and distinguishes driver handling for reference runtime and boot VID/PID pairs. The public package and README were located. The GUI was left unopened because the trace supplied no candidate DFU interface and no documented list-only CLI was found. The instrument was independently checked with dfu-util listing. [Official DreamDFU package](https://www.docs.dream.fr/progsam/index.php?racine=./Dream_DFU_Tools)
- **Upload support.** USB DFU runtime is class/subclass/protocol `fe/01/01`; DFU mode is `fe/01/02`. The functional descriptor uses bit 1 of `bmAttributes` for CanUpload. Upload support needs an attributable DFU-mode identity, affirmative descriptor or vendor evidence, and a documented unprotected target region. No functional descriptor turned up; the Dream guide gives no EWI-specific readback workflow. If those prerequisites are met, perform two independent read-only acquisitions to private files and compare sizes, byte equality and SHA-256. Completeness still depends on whether the authorized read includes bootloader, application, sound bank and calibration regions. [USB-IF DFU specification](https://www.usb.org/document-library/device-firmware-upgrade-11-new-version-31-aug-2004)
- **Dream RPC and other USB paths.** The public programmer documentation requires firmware implementing RPC and describes a separate reference USB interface. The current descriptor tree exposes no candidate. The DreamBlaster X2 loader demonstrates MIDI-based firmware identification on that model, but no firmware identification payload was documented for this EWI. Universal MIDI Identity has already timed out. No standard USB firmware version field was established. [Dream programmer downloads](https://www.docs.dream.fr/progsam/index.php?racine=./USB_RPC_Programmer_Tool) · [Prior Dream ecosystem survey](dream-ecosystem.md) · [Identity experiment](../experiments/2026-11-26-usb-midi-output.md)
- **BLE OTA.** No extra service UUID was returned to compare with documented implementations such as Silicon Labs OTA. A distinct service visible only in a special mode remains possible. The standard BLE MIDI I/O characteristic is evidence of the MIDI profile. [Silicon Labs OTA profile](https://docs.silabs.com/mcu-bootloader/latest/using-gecko-bootloader-with-bluetooth-apps/03-bluetooth-ota-upgrade)

## Service controls, applications and attribution

The DC02 and DC02 Pro manuals describe ordinary startup plus a dedicated Reset function that restores defaults. Targeted English, Chinese and Japanese searches for the candidate models, teardown, startup and upgrade terms found no revision-matched, evidenced service chord. The monitor's guided modes therefore use normal power and cable sequencing. The Reset control and speculative multi-button holds were excluded. [Konix DC02 Pro manual](https://file.globalso.com/file_manage/812/20240607/dc02-pro-instructions.pdf) · [科汇兴 DC02 中文说明书](https://www.konixtech.cn/resources/upload/a9358a00faa236b/t/1721121571353/DC02%E4%B8%AD%E6%96%87%E8%AF%B4%E6%98%8E%E4%B9%A6.pdf)

Konix's downloads list manuals for its wind products. The manuals name GarageBand and other general MIDI apps for connecting and playing. Searches of manufacturer support, model names and app-store listings turned up no attributable EWI service app or firmware package. The similarly branded Konix app found during the search is a guitar companion. The EWI-Clarinet modification project identifies DC02/DC02 Pro donor units, but gives no readable chip identification for the tested hardware or factory update. [Konix downloads](https://www.konixtech.com/download/) · [Konix guitar app](https://guitar.hiband.cc/) · [EWI-Clarinet project](https://www.ewi4christ.com/post/ewi-clarinet-project)

The Shenzhen Konix FCC grantee index contains an ED01 **drum kit** with internal photographs, but the reviewed grants contain no exact DC02 or DC02 Pro entry. The MK wind instrument grant has internal photographs and a different grantee (Shenzhen Shengyang) and model. Neither can establish the tested board or the Kalezo attribution. Search scope covered exact candidate model strings and applicant names in public indexed exhibits; a module filing under another company remains possible. [FCC search](https://www.fcc.gov/oet/ea/fccid) · [Konix grantee exhibits](https://fccid.io/2AX4N) · [ED01 photos](https://fccid.io/2AX4N-ED01/Internal-Photos/Internal-Photos-7938580) · [MK photos](https://fccid.io/2BLECMK/Internal-Photos/Internal-Photos-8271136)

A non-invasive path can reopen with an attributable exterior regulatory identifier, a confirmed OEM or seller-provided service document, or a trace from an evidenced service boot. The current evidence does not support issuing any Dream vendor request to the sample.
